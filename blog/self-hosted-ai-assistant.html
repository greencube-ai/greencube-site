Desktop First Private Self Hosted AI Assistant: 3 Deployment Paths

By Hector Gras · 4 September 2026

Yes, you can run a private AI assistant on your own hardware, and there are three practical ways to do it. A desktop app gets you chatting offline in minutes with no setup. A self-hosted server with a web interface gives you full control and lets several people share it. A hybrid setup keeps your documents local and sends only the hardest questions to a cloud model. Which one fits depends on your skills, your hardware and how private your data is.

I build GreenCube, a desktop app, so I lean towards the first path. Weigh my opinion with that in mind. The other two are good choices for the right person, and I'll describe them fairly.

Which path fits you

A desktop app suits you if you want it working today, don't want to touch a terminal, and are happy with fewer settings to tweak. It installs like any program, downloads a model, and that's it.

A self-hosted server suits you if you already use Docker, want several people to use the same assistant from their browsers, or want to build your own document search. Expect a weekend to get it running and some upkeep after that.

A hybrid setup suits you if some of your work is sensitive and some needs the reasoning of a large cloud model. You keep files local and send selected questions out. It's the most flexible and the easiest to get wrong.

A few questions worth answering before you pick: what data will the assistant see, and does any of it have to stay on your premises? What does the tool send over the network, and when? Who will keep it updated? What happens to your chats if you uninstall it or change computers?

What's inside any self-hosted assistant

Every setup, simple or complex, has the same four parts. Knowing them tells you what you're trusting with your data, even if you buy a packaged app.

  1. The model runner does the actual work. llama.cpp is the open-source engine many tools build on; Ollama and LM Studio wrap it with model downloads and a simpler interface. Many runners offer an OpenAI-compatible API, so other apps can talk to them.
  2. The front end is where you type. A desktop app bundles it; a web interface (Open WebUI is a popular one, see its alternatives) lets anyone on your network use it from a browser.
  3. Storage holds chat history and, if you search your documents, a vector database. Postgres with the pgvector extension is a common, practical choice because it handles both.
  4. Connectors link the assistant to email, calendars or folders. Each one is useful and each one is another place data can travel, so add them only when you need them.

How much hardware you need

The model has to fit in memory, and bigger models need more. On a laptop without a graphics card, small models in the 2 to 4 billion parameter range are what's comfortable; a graphics card with 6 GB or more of video memory makes larger ones practical. Running models at reduced precision (quantization) shrinks them a lot with a small loss in quality, and it's how almost everyone runs local AI.

Setting it up: three recipes

1. A desktop app (GreenCube as the example)

  1. Download the installer and run it on Windows 10 or 11.
  2. Sign in once with Google or Microsoft. This only checks that you paid.
  3. On first launch the app checks your PC and downloads the model that fits: Cube 2B on smaller PCs, Cube 4B if you have a graphics card.
  4. Start chatting or drop in a PDF. From here it works offline.

Most of the wait is the download.

2. A server with a web interface

  1. Install a model runner such as Ollama or llama.cpp on a machine with enough memory for your model.
  2. Point a web interface at the runner's API address.
  3. If you want document search, add Postgres with pgvector (or another local vector database) and a local embedding model.
  4. Load a few documents and test the answers before trusting it with real work.
  5. Keep the server behind your firewall, closed to the internet unless you deliberately set up secure remote access.

3. Hybrid, local plus cloud

  1. Run storage and document search locally, as in recipe 2.
  2. Decide which questions may go to a cloud model, and write that rule down.
  3. Remove names and other identifiers before anything leaves your machine.
  4. Log which questions went out, so you can check later.

One wrong routing rule can send something you meant to keep local, so test the redaction before you rely on it.

What "private" means here

Almost no tool has zero network traffic forever. A desktop app usually needs to download its model and check a licence; a server needs updates. The useful question is what goes out, and when. A tool that needs your chats to leave the machine to work is a different thing from one that only checks a licence.

GreenCube, for example, goes online to sign you in, to download the AI on first launch, to check for updates, and for web searches if you switch Online on. Your chats, files and images are saved on your PC. If you run a hybrid setup, every cloud call is a point where data leaves, so keep API keys out of config files you share and treat the cloud provider's data policy as part of your setup.

Common problems and fixes

  • The model won't load: check that the file format matches your runner. Most local tools expect GGUF.
  • The PC freezes or the app crashes: you're probably out of memory. Close other programs or use a smaller model.
  • Answers slow down after a change: a larger context window uses much more memory, so check that setting first.
  • The document index disappears after an upgrade: back up the vector database before upgrading anything.

Why I think most people should start with a desktop app

A lot of self-hosting advice assumes you enjoy tinkering. If you do, the server path is rewarding and gives you control over every piece. But many people just want a private place to ask questions and read a PDF without a subscription, and for them, Docker and vector databases are a lot of work for the same result.

It's a single-person desktop app, not a server your team connects to, and it won't out-reason a large cloud model on the hardest problems. If you need shared access or custom pipelines, build the server.

Questions

Can you self-host your own AI?

Yes. Run a model runner like Ollama or llama.cpp on your own hardware with a web interface on top, or install a desktop app that sets it up for you; either way your chats stay on your machine.

Can I build my own personal AI assistant?

Yes, with open-source parts: a local model runner, a front end, and a vector database if you want to search your documents. If these tools are new to you, expect a weekend to get a first version going.

How much does a personal AI assistant cost?

A desktop app like GreenCube is €9.99 once. Open-source setups are free apart from your hardware and time, and cloud APIs charge per use, which adds up with heavy document work.

Can I build my own AI agent for free?

Yes. Open-source model runners and front ends are free; you need hardware that can run the model, and time to set up document search and any connectors yourself.

What's the difference between a desktop AI app and a self-hosted server?

A desktop app like GreenCube is one package for one person on one PC. A self-hosted server splits the model runner, storage and web interface into parts you set up and maintain yourself, usually so several people can share it.
