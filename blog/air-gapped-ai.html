Air Gapped AI: A Security Team's Deployment Guide

By Hector Gras · 1 August 2026

Air-gapped AI is an AI system that runs on machines with no path to the internet or any outside network. The model, the data and every answer stay inside that boundary, and anything that needs to come in, like a new model or a software update, is carried in deliberately and checked on the way. It's the strictest way to run AI, used for classified or tightly regulated work, and it costs real effort to keep up.

I build GreenCube, an offline AI app for Windows, so I spend a lot of time on the difference between "works offline" and "air-gapped". They are not the same thing, and the last section says plainly where GreenCube sits.

Air-gapped vs offline vs "isolated"

The words get used loosely, and the differences matter.

  • Offline means a device isn't connected right now, or an app can work without a connection. It could reconnect at any time.
  • Isolated or private-cloud setups (a VPC, an on-premises server behind a firewall) limit traffic with rules, but a route out still exists.
  • Air-gapped means there is no route out at all: no internet, no outside DNS, no vendor licence check, no time server on the public internet.

The test is simple to state: can any process on any machine inside the boundary start a connection that reaches something outside it? If the answer is yes under any condition, maintenance windows included, it isn't air-gapped.

What has to live inside the enclave

Nothing in the AI stack can reach outside at run time, and the list of things that quietly try is longer than most people expect. A typical enclave needs its own copy of:

  • the model weights, kept in an internal store with a record of where each file came from;
  • the inference server, such as vLLM, Text Generation Inference or llama.cpp;
  • embedding models and a vector database if you search documents (Qdrant, Milvus and pgvector all run locally);
  • a container registry and package mirrors, because pulling from Docker Hub or PyPI isn't possible;
  • an internal certificate authority, identity provider, time source and log storage.

Plan for backups inside the boundary as well, since there's no cloud to restore from.

How updates get in

Every update is a small project. The usual pattern is a staging machine outside the enclave that downloads the artifact, checks it against the publisher's checksum, scans it, records a software bill of materials (SBOM, in SPDX or CycloneDX format) and signs it with a key the enclave trusts. The bundle then crosses on a data diode (hardware that only lets data flow one way) or on tracked, encrypted removable media. Inside, it is checked again before anyone switches it on, and the whole trip is logged: who carried it, which media, when.

Many teams also wait a day before activating anything new, so a second person can repeat the checks.

When you actually need one

Classified systems, and some contracts covering Controlled Unclassified Information or critical infrastructure, may require physical isolation. Frameworks such as FedRAMP and CMMC define security controls (drawn from NIST SP 800-53 and NIST SP 800-171), but meeting them doesn't automatically mean an air gap. What decides it is your data's classification, your contract and your assessor, so ask them early.

If your real worry is a vendor reading or training on your data, an air gap is probably more than you need. A local model on a well-protected machine, or a private deployment with strict outbound rules, can answer that worry at a fraction of the cost.

How air-gapped AI projects fail

Most failures aren't attacks. They're hidden dependencies.

  • A document-search pipeline built with a framework's default settings calls an outside embedding API on the first query. It seems to work, and the boundary is broken.
  • A container looks up an outside hostname at start-up for a health check or licence check.
  • An inference server sends usage statistics or checks for new versions by default.
  • The system trusts the operating system's default list of public certificate authorities.
  • Someone plugs in a personal USB stick to copy one file.
  • Someone connects the machine "just once" for a missing package. After that, the honest move is to treat it as exposed and rebuild it from known-good media.

The fixes are enforced, not written down: block all outbound traffic at the host firewall and, on Kubernetes, with a NetworkPolicy that denies egress by default; watch for connection attempts with a host sensor such as Falco; sign artifacts; and keep a written procedure for media.

The cost of running one

You trade freshness for control. Cloud models update constantly; an air-gapped model updates when someone runs the transfer process, often monthly or quarterly, so it falls behind. Every update creates paperwork. You own the hardware, the power and the cooling. And the hardest part comes years in, when the people who built it have moved on and the transfer procedure is out of date. Name an owner for the update cycle before the first file goes in.

What auditors look for

They want evidence from the running system, and diagrams alone won't do. The single most useful check is a silence test: run a full workload, document search included, while capturing traffic at the host and at the physical switch. Any packet addressed outside the boundary is a finding. Add to that a comparison of each running container against the SBOM recorded when it came in, a trust store that holds only your internal certificate authority, and a DNS sinkhole that should receive no queries.

A short checklist for getting there:

  1. Write down the threat model, the data classification and the controls your framework requires.
  2. Stand up the internal pieces: model store, registry, mirrors, certificate authority, logging.
  3. Build the staging machine and the transfer procedure, with named people allowed to carry media.
  4. Enforce outbound blocking at the host and network level.
  5. Run the silence test before calling anything production, and again on a schedule.
  6. Keep transfer records, access logs and test results together for each review.

Where GreenCube fits, honestly

GreenCube is not an air-gapped product. It needs the internet once to sign in (only to check you paid) and to download the AI on first launch. After that it works with the network off, and it only goes online to check for updates, to keep your sign-in fresh while the PC is online, or for web lookups if you switch Online on. Your chats and files are saved on the PC.

That's a good fit for a lawyer, researcher or small team who wants an AI that doesn't keep their work on someone else's server. It doesn't meet a rule that says a machine may never touch a network, and it doesn't come with the signed-ingest process, internal certificate authority or audit logging an accredited enclave needs. If your work requires those, build the enclave described above.

Questions

What is air gapping in AI?

It means running an AI system on machines with no path to the internet or any outside network. The model, the data and every answer stay inside that boundary, and anything coming in, like a new model or an update, is carried in deliberately and checked.

What does "air-gapped" mean in tech?

An air-gapped system has no connection to any outside network at all: no internet, no outside DNS, no vendor licence check, no public time server. The name comes from the literal gap of air between it and any connected network.

What is the difference between air-gapped and offline?

Offline means a device isn't connected right now, or an app can work without a connection, and it could reconnect at any time. Air-gapped means there is no route out at all, under any condition, maintenance windows included.

Does GreenCube qualify as air-gapped AI?

When is a full enterprise air gap legally required?
