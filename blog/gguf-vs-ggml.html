GGUF vs GGML: Why One File Wins for Private Local AI

By Hector Gras · 10 October 2026

Use GGUF. It's the file format llama.cpp and the apps built on it use today: one file that holds the model's weights, its tokenizer and typed metadata, so tools can add new model types without breaking old files. GGML files are the older format it replaced. You'll still find them in old archives, but current tools don't load them, so look for a GGUF version of the same model instead.

One thing that confuses people: "GGML" is also the name of the C library that llama.cpp runs on (ggml-org/ggml). That library is very much alive. What's obsolete is the old GGML file format.

How the two formats differ

Both formats package a model so it can run on an ordinary computer. The difference is in how they describe the model.

GGML files stored the model's settings as a fixed, untyped list of values. That was fine for the first simple models, but every new architecture or tokenizer meant changing the list, and older files and newer code often stopped understanding each other. IBM's explainer names this as the reason GGML kept causing breaking changes.

GGUF replaced the list with named, typed key-value pairs. A new field doesn't disturb the old ones, and a reader can skip keys it doesn't recognise instead of failing. The file also carries the tokenizer, a version number and a fixed header, and its tensor data is aligned so a program can map the file straight from disk instead of copying it into memory first. The details are in the GGUF specification.

Is GGUF faster or smaller?

Not in itself. There are few honest head-to-head benchmarks of the two formats, and they wouldn't tell you much. How fast a model runs and how much memory it takes depend almost entirely on its size and on the quantization level (how many bits each weight is squeezed into), not on the container. A 4-bit build of a model needs much less memory than an 8-bit one, at some cost in quality. Our guide to quantization explains the trade-off.

Where GGUF does help is loading: one aligned file with everything inside opens quicker and with fewer surprises than a folder of separate config, tokenizer and weight files.

GGUF is built for running models, not training them. When Hugging Face Transformers loads a GGUF file, it turns the weights back into full 32-bit precision (Transformers docs), so the memory savings disappear if you fine-tune.

Which tools read GGUF

llama.cpp, Ollama, LM Studio, Jan and GPT4All all run GGUF files, and Hugging Face shows GGUF files directly on model pages. If a local AI app doesn't list GGUF support, that's a sign it isn't keeping up with current local models. GreenCube runs on llama.cpp too, so its models are GGUF files (Cube 2B, built on Gemma 4 E2B, and Cube 4B, built on Gemma 4 E4B); the app downloads the right one for your PC on first launch, so you never handle the file yourself.

Converting a model to GGUF

Most people never need to: popular models are published already converted, in several quantization levels, on Hugging Face. If you do want to convert one yourself:

  1. Download the original model from Hugging Face, including its config.json and tokenizer files.
  2. Run llama.cpp's convert_hf_to_gguf.py script on the folder to get a full-precision or 16-bit GGUF file.
  3. Shrink it with llama.cpp's quantize tool to the level you want, such as a 4-bit or 8-bit type.
  4. Load the result in llama.cpp, Ollama or LM Studio.

The usual snags are a missing config.json, the wrong Python version for the script, or a half-finished download. If the architecture is new and llama.cpp doesn't support it yet, conversion won't work until someone adds it, and that's real programming work. In nearly every case, a trusted pre-converted file is the faster route.

Is one format safer than the other?

The format doesn't change privacy: either way the model runs on your machine and your prompts stay there. What matters is where the file came from. Download models from sources you can identify, such as the original publisher or a well-known converter on Hugging Face, and keep your app up to date. GGUF's built-in metadata makes it easier to see what a file is. A stray .ggml file of unknown origin is harder to check, and you couldn't run it in a current app anyway.

Questions

Are GGUF models better than GGML models?

For anything you'd run today, yes. GGUF keeps the tokenizer and typed metadata in one file and is what current tools support; the model inside isn't smarter, it's just more compatible.

Can I still use old GGML files?

Only with old versions of the software that made them. Better to find a GGUF build of the same model, or a newer model, which will almost certainly be better anyway.

Does converting to GGUF reduce model quality?

Not at full or 16-bit precision. Quantizing to fewer bits does, a little at 8 bits and more as you go lower, but that's a size and speed choice separate from the format.

Do I need to convert models myself to use a tool like GreenCube?

No. GreenCube picks and downloads a ready-made model for your PC on first launch, with no converting or command line.

Why do some apps need more RAM to run local models than others?

Mostly because they run bigger or less compressed models. The model's size and quantization level decide most of the memory, plus a bit extra for the conversation it's keeping in mind.
