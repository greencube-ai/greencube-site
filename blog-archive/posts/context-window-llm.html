A context window is how much text a language model can take into account at once, measured in tokens. Everything counts: the instructions, the whole conversation so far, any documents you paste in, and the answer it's writing. A 200K window holds about 150,000 English words and a 1 million token window about 750,000. Bigger windows cost more memory, time and money, and models don't use every part of a long window equally well, so the biggest number isn't automatically the best choice.

Here's how context windows work, why they have limits, and how to work well within them, in the cloud or on your own PC.

Tokens, and what fills the window

A token is a chunk of text: sometimes a whole word, sometimes part of one, sometimes a punctuation mark. As a rule of thumb, 100 tokens is about 75 English words. Code and many other languages use more tokens for the same amount of text.

Everything in a request counts against the window:

  • the system prompt, the hidden instructions that set how the assistant behaves;
  • your question;
  • the conversation history, unless the app trims it;
  • any documents or search results added to the prompt;
  • the model's own answer, as it writes it.

When the window is full, something has to go. Some apps show an error; others quietly drop the oldest messages, and the model then answers as if they were never said.

GPT-3 had a 2,048-token window. Today many models offer 128K or more, and Google's Gemini documentation describes windows of 1 million tokens and beyond. These numbers change with almost every release, so check the model's own documentation, and the limits of the app or API you actually use, which can be lower than the model's maximum.

Why models have a maximum

The first limit is attention. Each token is compared with every other token, so the work grows with the square of the length: ten times more text means about a hundred times more attention work. Modern models use tricks to soften this, but long prompts still take longer before the first word of the answer appears.

The second is memory. While it writes, the model keeps a cache of what it has already read (the KV cache) so it doesn't redo that work for every new token. That cache grows with every token in the window, and it has to sit in fast memory next to the model. For big models with very long contexts it can reach tens of gigabytes.

The third is training. Models are trained on sequences up to a certain length. Stretching them past it can work, but quality often drops in ways you only notice when you test.

Where long context breaks down

A long window doesn't mean the model reads all of it equally carefully. The study "Lost in the Middle" found that models recall information at the start and end of a long prompt better than information in the middle. Put the key clause on page 40 of an 80-page contract and you're more likely to get a wrong answer than if it were on page one.

Cost and speed grow with length too. Cloud APIs charge per token on every request, so resending a huge document with each question adds up, and every extra token slows the first reply.

How to work within the limit

  1. Budget the window. Leave room for the instructions, the conversation and the answer you need, and see what's left for documents.
  2. Use retrieval instead of pasting everything. Retrieval (RAG) finds the passages that matter and puts only those in the prompt. It's usually cheaper, and often more accurate, than stuffing in the whole file.
  3. Reuse repeated context. Several cloud providers offer prompt or context caching, which makes a repeated long prompt cheaper and faster on later requests.
  4. Summarise old turns. In a long chat, replace early messages with a short summary instead of carrying the full transcript. Anthropic's guide to context engineering describes this kind of compaction, along with keeping structured notes outside the window.
  5. Test at your real length. If you'll send 30-page documents, test with 30-page documents, not a demo paragraph.

When a big window is worth it

Large windows earn their cost when the model really must see everything at once: summarising a whole report or book, reviewing a contract whose clauses refer to each other, or tracing a bug across many files of code.

They're a poor fit for quick chat, where people expect a fast reply, and for the same narrow question asked over and over against a big set of documents. There, retrieval almost always wins on cost and consistency.

Context windows on your own PC

When an AI runs on your own computer, the context window competes for the same RAM or graphics memory as the model itself, because the KV cache lives there too. So local apps usually use a window far smaller than the model's maximum, sized for the machine, and a very long conversation or document makes a local model slower as it goes. That's the trade for running offline: less room than a data centre, in exchange for your text never leaving your PC.
